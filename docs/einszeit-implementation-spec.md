# Einszeit Implementation Specification

**Document ID:** EZ-IMPL-001  
**Status:** Informative  
**Scope:** Einszeit firmware, host software, and hardware interface design

---

## 0. Purpose

This document describes implementation guidance for the Einszeit system. It complements EZ-SEC-001, which defines the core security invariants. This document covers architecture, storage layout, metadata format, protocols, CLI design, and optional features such as forward secrecy.

---

## 1. Architecture

### 1.1 Hardware Abstraction Layer (HAL)

The implementation MUST be hardware-agnostic. All hardware interfaces MUST be decoupled from the core API:

- TRNG, SPI, UART, USB, and memory interfaces MUST each be accessed through a defined HAL.
- The core API MUST NOT reference specific hardware peripherals, register addresses, or vendor SDKs directly.
- Switching MCU, entropy source, or storage medium MUST require only a new HAL implementation, with no changes to the core API.

### 1.2 Core API

The core API performs all security-sensitive operations:

- Key generation and entropy testing
- Session management (create, import, list, delete)
- Encryption and decryption
- OTP offset management

The core API is the only component permitted to access key data storage. No other layer may read or write key material directly.

### 1.3 Transport Layer

The core API MAY be accessed over multiple transports:

- USB HID
- USB ACM (serial)
- UART
- Other custom protocols

The transport layer MUST be a thin adapter that serialises and deserialises requests to and from the core API. It MUST NOT implement any security logic itself.

## 2. Key Data Storage

Key data is stored as files on a FAT filesystem (FatFS). This applies to both storage media:

- **NOR flash key partition** (2MB): formatted with FatFS at first use.
- **MicroSD card**: formatted with FatFS; used for both active session storage and as a key transfer medium.

### 2.1 Key Files

A key file contains only raw random bytes — no header, no metadata. This ensures compatibility with key material generated by any TRNG source, not just Einszeit devices.

Key files are named using the Key ID in hexadecimal with a `.KEY` extension (e.g., `A73F2C01.KEY`). The Key ID is out-of-band metadata conveyed by one of the following means, in order of preference:

1. **Filename:** Both parties use the same filename during exchange; the Key ID is read directly from it.
2. **Manual:** The Key ID is communicated separately (verbally, on paper, etc.) and entered by the user at session creation time.
3. **None:** If no Key ID is available, Key ID `0x00000000` is used. The user must specify the filename explicitly at session creation and must select the session manually by label during decryption.

### 2.2 Session Label

At session creation, the user MUST provide a human-readable label for the session (e.g., `"Bob"` or `"Office"`). This label is stored in the session record and is the primary means of identifying a session in the UI and CLI. It has no cryptographic significance.

### 2.3 Storage Selection

The device supports multiple drives for key storage. Drive 0 (NOR flash key partition) is always available. MicroSD drives are only available when a card is inserted. Drive 0 is the default for key generation when no drive is specified.

Keys and sessions are independent:

- A key is a file on a drive. It can be generated, copied, and deleted independently of any session.
- A session is a local record that links to a key on a specific drive. Creating a session does not copy or move the key — it records the drive index and filename.
- Deleting a key that is linked to an active session MUST warn the user before proceeding. If confirmed, the session MUST be set to `QUARANTINED` since its key file no longer exists.

## 3. Metadata Storage (F-RAM)

Session metadata is stored in F-RAM. F-RAM supports byte-level writes with high endurance (≥10¹² write cycles), making it suitable for frequent OTP offset updates.

### 3.1 F-RAM Layout

The 2KB F-RAM begins with a fixed-size device record, followed by session slots.

```
Offset  Field
0       Device record (32 bytes)
32      Session slot 0
32+S    Session slot 1
...     ...
```

Where S is the session slot size.

### 3.2 Device Record

The device record stores device-wide state and is updated independently of session records.

```
Offset  Length  Field
0       2       Magic: 0x455A ("EZ")
2       1       Format version
3       1       Reserved
4       4       Boot counter (incremented on each power-on; unexpected increments may indicate the device was accessed without the user's knowledge)
8       4       Device flags
12      16      Reserved
28      4       CRC32 of bytes 0–27
```

Total size: 32 bytes.

### 3.3 Session Record Format

Each session slot contains:

```
Offset  Length  Field
0       2       Magic: 0x455A ("EZ")
2       1       Status: 0x00=empty, 0x01=VALID, 0x02=QUARANTINED,
                        0x03=EXHAUSTED, 0x04=ZEROIZE_PENDING (see §6)
3       1       Feature flags (bit 0: forward secrecy enabled)
4       1       Drive index (0=NOR flash, 1=MicroSD, 2=MicroSD2)
5       1       Offset selector (0x00=offset A is current, 0x01=offset B is current)
6       1       Role (0x00=alice, 0x01=bob)
7       1       Reserved
8       4       Key ID (0x00000000 if not known)
12      4       Key length in bytes
16      4       OTP offset A
20      4       OTP offset B
24      16      Human-readable label (UTF-8, null-terminated)
40      4       Reserved
44      4       CRC32 of bytes 0–43
```

Total slot size: 48 bytes. At 48 bytes per slot, 2KB F-RAM accommodates up to 41 sessions after the 32-byte device record.

On power-on, if the key file is accessible, the firmware MUST verify that the actual file size matches the key length stored in the session record. A mismatch MUST cause the session to be set to `QUARANTINED` before any operation is permitted.

The key is partitioned at its midpoint. Alice starts at offset 0 and consumes forward; bob starts at `key_length / 2` and consumes forward. This allows both parties to encrypt independently without offset collision. The key generator is alice by default; the recipient is bob by default. Both roles may be overridden at session creation time.

The key filename is derived from the Key ID as `<KEY_ID_HEX>.KEY` (e.g., `A73F2C01.KEY`). When Key ID is `0x00000000`, the firmware cannot infer the filename and must prompt the user to specify it at session creation time. The filename is not stored in the session record.

### 3.4 Offset Update Atomicity

The session record holds two OTP offset slots (A and B) and a single-byte selector indicating which is current. Since a single-byte F-RAM write is inherently atomic, flipping the selector is the entire commit — no recovery step is needed on power-on.

Update sequence:

1. Write new offset value to the inactive slot (the one not indicated by the selector)
2. Read back the inactive slot and verify it matches the intended value — if verification fails, abort; the current offset is unchanged
3. Flip the selector byte (atomic) — the new offset is now live

Power loss before step 3 leaves the selector pointing to the old offset, which remains valid. Power loss after step 3 means the new offset is already live. In either case the device is in a consistent state on next power-on with no recovery logic required.

## 4. Core API

The core API defines all device operations. Each command has a canonical code used by all transports. The CLI maps subcommands to these codes; the HID and ACM transports carry them directly.

### 4.1 Session Commands

| Code | Command | Description |
|---|---|---|
| `0x01` | `SESSION_LIST` | Return all session records |
| `0x02` | `SESSION_CREATE` | Create a session linked to an existing key file on a drive; role defaults to alice for the generator, bob for the recipient |
| `0x03` | `SESSION_DELETE` | Delete a session record (does not delete the key file) |
| `0x04` | `SESSION_INFO` | Return details for one session |

### 4.2 Key Commands

| Code | Command | Description |
|---|---|---|
| `0x10` | `KEY_GENERATE` | Generate a new key file on a specified drive (default: drive 0) |
| `0x11` | `KEY_COPY` | Copy a key file from one drive to another |
| `0x12` | `KEY_DELETE` | Delete a key file from a drive; warns if linked to an active session |

### 4.3 Crypto Commands

| Code | Command | Description |
|---|---|---|
| `0x20` | `ENCRYPT` | Encrypt a message using a session |
| `0x21` | `DECRYPT` | Decrypt a message using a session |

### 4.4 Drive Commands

| Code | Command | Description |
|---|---|---|
| `0x30` | `DRIVE_LIST` | List key files on a specified drive |
| `0x31` | `DRIVE_INFO` | Return drive index, type, capacity, and free space |

### 4.5 Test Commands

| Code | Command | Description |
|---|---|---|
| `0x40` | `ENTROPY_TEST` | Run post-generation entropy test on a key file |
| `0x41` | `RANDOM` | Return N bytes of raw TRNG output |

### 4.6 Device Commands

| Code | Command | Description |
|---|---|---|
| `0x50` | `DEVICE_INFO` | Return firmware version, hardware revision, drive status |
| `0x51` | `DEVICE_ERASE` | Initialize or factory reset the device: formats the NOR flash key partition, initializes the F-RAM device record and session slots, and erases all key files on all drives. Safe to run on first use. |

## 5. Message Format

Messages are encoded as base64 for transport over any text-capable channel.

Binary structure before base64 encoding:

```
Field           Length  Notes
Magic           2       0x455A ("EZ")
Key ID          4       Identifies which key was used (optional; may be 0x00000000)
OTP offset      4       Byte offset into key where encryption began
Message length  4       Length of plaintext in bytes
Ciphertext      N       Encrypted payload
CRC32           4       CRC32 of all preceding fields
```

Total overhead: 18 bytes + N bytes ciphertext.

The Key ID field MAY be set to zero if both parties have agreed on session selection out-of-band. See EZ-SEC-001 SEC-ENC-004.

## 6. Forward Secrecy Feature

Forward secrecy is an optional per-session feature controlled by bit 0 of the feature flags byte in the session record. When enabled, consumed key bytes are erased after use. When disabled, key bytes are retained and past messages remain decryptable.

Forward secrecy is disabled by default.

### 6.1 Erase Strategy for Block-Erase Media

NOR flash cannot overwrite individual bytes — the minimum erase unit is a block (implementation-defined parameter, e.g., 4KB). To ensure that erasing consumed bytes never affects an adjacent key:

- **IMPL-FS-001:** Each key file MUST be allocated such that its byte range does not share an erase block with any other key file. FatFS cluster size MUST be set to the flash erase block size or a multiple thereof.
- **IMPL-FS-002:** The erase block size MUST be a runtime or compile-time parameter. It MUST NOT be hardcoded in hardware-agnostic code.
- **IMPL-FS-003:** Consumed bytes MUST be erased one block at a time as the OTP offset advances past each block boundary. The current (partially consumed) block MUST NOT be erased until the offset advances past it entirely.

### 6.2 Power-Loss Recovery

- **IMPL-FS-004:** Before erasing a block, the firmware MUST set the session status to `ZEROIZE_PENDING` in F-RAM.
- **IMPL-FS-005:** After erasure is verified by read-back, the firmware MUST set the session status back to `VALID` and update a "last erased block" pointer in the session record.
- **IMPL-FS-006:** On power-on, any session with status `ZEROIZE_PENDING` MUST automatically resume erasure from the last erased block pointer before the session becomes available. No user action is required.

### 6.3 Removable Media Limitation

MicroSD cards use internal wear levelling and do not guarantee that a logical block erase destroys the physical data. Forward secrecy over MicroSD provides best-effort erasure only. The UI MUST inform the user of this when forward secrecy is enabled on a MicroSD-backed session.

## 7. Transports

### 7.1 USB HID

The device presents as a USB HID device. All commands are exchanged as 64-byte HID reports.

Report format:

```
Offset  Length  Field
0       1       Report ID (always 0x00)
1       1       Command code (see §4)
2       1       Session slot index (0xFF if not session-specific)
3       1       Flags / Status
4       2       Payload length
6       58      Payload
```

Payloads larger than 58 bytes are split across multiple reports using a sequence number in the flags field. A final-packet flag indicates the last report in a sequence.

### 7.2 USB ACM / UART

Commands may also be issued over USB ACM (serial) or UART using a simple framed text or binary protocol. The same command codes (§4) apply. This transport is also used by the on-device CLI.

## 8. CLI

### 8.1 Host CLI

A command-line utility (`ez`) MUST be provided for Windows, Linux, and macOS. It communicates with the device over USB HID or USB ACM and delegates all operations to the core API (§4).

### 8.2 On-Device CLI

A lightweight CLI runs natively on the device, accessible over USB ACM. It exposes the same commands as the host CLI without requiring a host application.

### 8.3 Commands

| Command | API | Description |
|---|---|---|
| `ez session list` | `SESSION_LIST` | List all sessions (Key ID, label, offset, status, remaining capacity) |
| `ez session create <label> <filename> [--drive <n>] [--key-id <id>] [--role <alice\|bob>]` | `SESSION_CREATE` | Create a session linked to an existing key file; role defaults to alice if omitted on the generating device, bob otherwise |
| `ez session delete <label>` | `SESSION_DELETE` | Delete a session record (does not delete the key file) |
| `ez session info <label>` | `SESSION_INFO` | Show full session details |
| `ez key generate [--drive <n>] <length>` | `KEY_GENERATE` | Generate a new key file on a drive (default: drive 0) |
| `ez key copy <filename> --from <n> --to <n>` | `KEY_COPY` | Copy a key file between drives |
| `ez key delete <filename> --drive <n>` | `KEY_DELETE` | Delete a key file; warns if linked to an active session |
| `ez drive list [--drive <n>]` | `DRIVE_LIST` | List key files on a drive; lists all drives if n omitted |
| `ez drive info [--drive <n>]` | `DRIVE_INFO` | Show drive type, capacity, and free space |
| `ez encrypt <label>` | `ENCRYPT` | Encrypt stdin, output base64 to stdout |
| `ez decrypt <label>` | `DECRYPT` | Decrypt base64 from stdin, output plaintext to stdout |
| `ez device info` | `DEVICE_INFO` | Show firmware version, drive status, session count |
| `ez device erase` | `DEVICE_ERASE` | Initialize or factory reset the device: formats NOR flash, initializes F-RAM metadata, erases all key files on all drives. Safe to run on first use. |
| `ez test entropy` | `ENTROPY_TEST` | Run entropy test on TRNG output |
| `ez test random [N]` | `RANDOM` | Output N bytes of raw TRNG data (default 32) |

### 7.4 Compatibility Note

V0 used a single `ez` binary with short flags (`-i`, `-c`, `-w`, `-r`, `-E`, `-R`) and a fixed alice/bob identity model. V1 replaces this with the subcommand structure above. The V0 identity model (alice/bob fixed roles, single key pair) is superseded by the V1 multi-session model.

## 9. Development TODO

The following items are required to bring the V1 implementation to a complete and auditable state, in approximate priority order:

1. **Refactor firmware** — rewrite firmware for new hardware, improved reliability and full enforcement of OTP constraints as defined in EZ-SEC-001 and features from EZ-IMPL-001. Support the ability to test all features.
2. **Refactor host CLI** (`ez`) — rewrite for reliability, V1 multi-session support and features from EZ-IMPL-001, and OTP constraint enforcement; replace V0 single-session alice/bob identity model. Add support for an interactive version of the CLI in a way that can be directly compiled with the firmware to provide an interactive on-device CLI.
3. **Develop on-device CLI** — integrate lightweight CLI accessible over USB ACM, into the firmware exposing the same commands as the host CLI. This should be optional because USB composite devices may require custom driver support on Windows. Ideally we can choose at compile time between USB HID, USB ACM or USB HID + USB ACM.
4. **Automated test suite** — covers both firmware and host CLI; must include OTP offset integrity, session isolation, replay detection, entropy validation, and power-loss recovery scenarios.
5. **Human code review and audit** — full review of firmware, CLI, and protocol implementation resulting in a written audit report and resolution of all identified security issues.
6. **Experimental web interface** — browser-based UI using WebHID API; no security logic on the host side.
7. **Experimental Android app** — side-loadable native app communicating with the device over USB HID; no security logic on the host side.
